Description:
The IGDB refresh background job processes stale games in batches of up to 500.
For each batch it loops over every game ID one at a time and, inside that loop,
issues several individual database queries (fetch the game row, fetch its
time-to-beat row, delete and re-insert its genre and platform links, look up
each genre/platform/external row by primary key). That turns one batch into
thousands of small sequential round-trips to SQL Server instead of a handful
of set-based queries. The job still produces correct results because all of
the work happens inside a single transaction per batch and the job runs
infrequently in the background, so the extra latency (typically seconds per
batch) is tolerable today. The concern is scalability and convention: as the
library grows to many batches, total refresh time grows linearly with per-game
queries, and the codebase standard is to batch-load with WHERE ... IN (...) up
front. A future change should load each batch's games and related rows once,
then apply the updates in memory before committing.
